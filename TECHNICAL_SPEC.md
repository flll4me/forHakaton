# 2. ОПИСАНИЕ ПРОЕКТА

Grand Mobile Support Copilot — интеллектуальная система предварительной обработки обращений игроков мобильной игры Grand Mobile.

Система должна автоматически:

1. Определять язык обращения.
2. Определять тип, категорию и приоритет обращения.
3. Выявлять спам и повторные обращения.
4. Извлекать структурированные сведения из текста.
5. Находить соответствующие пункты правил игры посредством RAG.
6. Генерировать черновик ответа на языке игрока.
7. Проверять достоверность ссылок на правила.
8. Определять необходимость передачи обращения администратору.

Система не должна самостоятельно принимать окончательные решения о наказании игроков, разблокировке аккаунтов и возврате средств.

Это интеллектуальный помощник администратора, а не полностью автономная система модерации.

## 2.1. Основные ограничения

- Нет доступа к исходному коду Grand Mobile.
- Нет доступа к игровым серверам, API и производственным базам.
- Используются исключительно предоставленные анонимизированные данные.
- Интеграция с игрой будет осуществляться разработчиками Grand Mobile.
- Внешние LLM API разрешены.
- Стоимость обработки одного обращения не должна превышать $0.002 либо необходимо использовать локальную модель.
- P95 latency должен быть не более 5 секунд.

## 3.1. Схема обращения

Пример исходной записи:

```json
{
  "ticket_id": "5b2e...",
  "kind": "complaint",
  "created_at": "2026-03-14T19:02:00",
  "region": "kz",
  "server_lang": "kk",
  "lang": "ru",
  "reporter_hash": "a91c...",
  "reported_hash": "7f3e...",
  "reported_nick": "Arman_Petrov",
  "rule_refs_raw": "2.1",
  "images_count": 2,
  "messages": [
    {
      "role": "player",
      "ts": "...",
      "text": "оскорбил меня и семью, скрины есть"
    },
    {
      "role": "reported_player",
      "ts": "...",
      "text": "это была игра по роли"
    },
    {
      "role": "admin",
      "ts": "...",
      "text": "Жалоба одобрена..."
    }
  ],
  "verdict": "approved",
  "punishment": "мут на 30 минут",
  "violation": "2.1 ОП",
  "category": null,
  "priority": null
}
```

Важно:
- Не считать `reported_player` и `admin` сообщениями заявителя.
- Не путать `reporter_hash` и `reported_hash`.
- Не считать `rule_refs_raw` подтверждённым нарушением.
- Не считать текст жалобы установленным фактом.
- Не считать наличие скриншотов подтверждением нарушения.

## 3.2. Особенность разметки

В официальном задании категории и приоритеты тренировочного набора не размечены. Валидационный набор также не следует считать размеченным по этим полям без проверки реального содержимого.

Необходимо исследовать возможность получения слабой разметки на основе:
- verdict;
- punishment;
- violation;
- kind;
- текста обращения;
- taxonomy.json.

Не использовать автоматически извлечённые метки как безусловно правильные.

Создать отдельную методологию weak supervision и оценивать качество полученной разметки.

Если отсутствуют достоверные метки, не заявлять Accuracy и Macro-F1 как результаты проверки на истинной разметке. Создать проверяемую вручную контрольную выборку.

# 5. АРХИТЕКТУРА СИСТЕМЫ

Реализовать модульную архитектуру.

Основной поток обработки:

INPUT
→ PREPROCESSING
→ LANGUAGE DETECTION
→ CLASSIFICATION
→ FACT EXTRACTION
→ DEDUPLICATION
→ RAG RETRIEVAL
→ RESPONSE GENERATION
→ SAFETY VALIDATION
→ OUTPUT

Каждый компонент должен быть независимым модулем с чётким интерфейсом.

Не реализовывать всю бизнес-логику внутри одного endpoint или одного огромного класса.

## 5.1. Preprocessing

Файл: `normalizer.py`

Функции:
- очистка лишних пробелов;
- нормализация Unicode;
- обработка пустых сообщений;
- удаление технического мусора;
- нормализация CP1251-представления казахских букв;
- сохранение исходного текста;
- подготовка нормализованного текста для ML и RAG.

Особое внимание уделить казахским буквам:

| Входящий символ | Нормализованный |
|---|---|
| ќ | қ |
| ґ | ғ |
| ѕ | ң |
| є | ә |
| ј | ө |
| ў | ұ |
| ї | ү |

Реализовать преобразование отдельной функцией с unit-тестами.

Не изменять исходные данные.

Предусмотреть сохранение двух представлений:
- original_text;
- normalized_text.

## 5.2. Language Detection

Файл: `language_detector.py`

Поддерживаемые языки:
- ru — русский;
- kk — казахский;
- uz — узбекский;
- en — английский;
- es — испанский;
- pt — португальский;
- und — неопределённый.

Фактическое распределение языков проверить на датасете.

Поле `lang` из исходной записи использовать как вспомогательный признак, но не считать абсолютной истиной.

При возможности использовать fastText или Lingua.

Предусмотреть:
- короткие сообщения;
- опечатки;
- смешанные языки;
- транслитерацию;
- сообщения без достаточного количества языковых признаков.

Если уверенность недостаточна, возвращать `und`.

Не переводить обращения без необходимости.

## 5.3. Classification

Файл: `classifier.py`

Основные задачи:

1. Определение категории.
2. Определение приоритета.
3. Определение типа обращения.
4. Выявление спама.

Использовать категории строго из taxonomy.json.

Не создавать собственную несовместимую таксономию.

Сравнить несколько подходов:

A. TF-IDF + Logistic Regression.

B. TF-IDF + Linear SVM.

C. Multilingual embeddings + классификация.

Предпочтительный вариант — гибридная архитектура с возможностью выбора наиболее эффективной модели по результатам экспериментов.

Для коротких сообщений использовать символьные n-граммы.

Приоритеты:
- P0 — критический;
- P1 — высокий;
- P2 — средний;
- P3 — низкий.

Конкретные критерии определения приоритета брать исключительно из taxonomy.json.

Для неоднозначных обращений использовать низкую confidence и передавать человеку.

Подготовить:
- обучающий скрипт;
- сохранение модели;
- загрузку модели;
- скрипт оценки;
- таблицу результатов сравнения моделей.

## 5.4. Fact Extraction

Файл: `fact_extractor.py`

Извлекать:

- nickname;
- rule_refs;
- has_evidence;
- server;
- дополнительные структурированные факты при наличии.

Использовать:
- регулярные выражения;
- исходные поля обращения;
- контекст сообщений;
- при необходимости LLM с ограниченной JSON-схемой.

Правила:

1. Никнейм из `reported_nick` имеет приоритет для соответствующего поля.
2. `images_count > 0` означает наличие вложений, а не подтверждение нарушения.
3. Номера правил из `rule_refs_raw` являются заявленными игроком.
4. Извлечённые факты не должны превращаться в подтверждённые вердикты.
5. Отсутствующие сведения возвращать как null.

## 5.5. Deduplication

Файл: `deduplicator.py`

Бонусная функция.

Требуется обнаруживать повторные обращения одного игрока по одной проблеме.

Условия из задания:
- один игрок;
- одна проблема;
- пять обращений;
- временное окно один час.

Использовать:
- reporter_hash;
- created_at;
- kind;
- семантическую схожесть текста;
- reported_hash, если применимо.

Реализовать сравнение обращений с помощью embeddings либо другого подходящего алгоритма.

Не считать два обращения дубликатами только потому, что они содержат одинаковые общие слова.

Возможные результаты:
- duplicate;
- related;
- new_issue.

Если данных недостаточно, не утверждать, что обращение является дубликатом.

# 6. RAG — БАЗА ЗНАНИЙ

Файл: `rag.py`

RAG обязателен по условиям кейса.

Использовать rules.json как основной источник правил.

## 6.1. Индексация

1. Прочитать rules.json.
2. Изучить фактическую структуру.
3. Извлечь самостоятельные пункты правил.
4. Сохранить исходные идентификаторы.
5. Сохранить исходный текст.
6. Построить индекс.

Каждый пункт должен иметь структуру:

{
  "rule_id": "2.1",
  "section": "Общие правила",
  "text": "Исходный текст правила"
}

Пример условный. Фактическое содержимое брать из rules.json.

## 6.2. Поиск

Реализовать гибридный поиск:

- BM25;
- FAISS;
- multilingual embeddings.

Объединять результаты и ранжировать по релевантности.

Возвращать ограниченное количество наиболее релевантных правил.

Не использовать весь документ с правилами в каждом запросе.

## 6.3. Контроль цитирования

Каждое правило, указанное в черновике ответа, должно:
- существовать в базе;
- иметь корректный идентификатор;
- присутствовать в результатах поиска;
- соответствовать содержанию обращения.

Реализовать отдельную функцию:

validate_citations()

Она проверяет существование и допустимость ссылок.

Если проверка не пройдена:
- не принимать ответ как достоверный;
- установить needs_human = true;
- записать причину.

Никогда не генерировать вымышленные номера правил.

# 7. RESPONSE GENERATION

Файл: `response_generator.py`

Генератор формирует черновик ответа.

На вход передавать:
- исходное обращение;
- нормализованный текст;
- язык;
- категорию;
- приоритет;
- извлечённые факты;
- результаты RAG;
- инструкции безопасности.

## 7.1. Требования к генерации

Ответ должен:
- быть на языке игрока;
- быть понятным;
- быть нейтральным;
- не содержать неподтверждённых обвинений;
- не обещать результатов, которые система не контролирует;
- содержать ссылки на правила, если они необходимы.

Для типовых обращений можно использовать шаблоны.

Для сложных случаев использовать LLM.

Не использовать генеративную модель там, где достаточно детерминированного шаблона.

## 7.2. Запрещённые обещания

Система не должна обещать:

- разблокировку аккаунта;
- возврат денежных средств;
- обязательное наказание другого игрока;
- гарантированное удовлетворение жалобы;
- гарантированный результат апелляции.

Не выдавать решение администратора от имени системы.

## 7.3. Пример

Вход:

{
  "kind": "complaint",
  "messages": [
    {
      "role": "player",
      "text": "Arman_Petrov оскорблял меня и мою семью в чате, скрины есть, 2.1 ОП",
      "attachments": 2
    }
  ]
}

Пример допустимого результата:

{
  "lang": "ru",
  "category": "complaint.insult",
  "priority": "p2",
  "is_spam_or_duplicate": false,
  "extracted": {
    "nickname": "Arman_Petrov",
    "rule_refs": ["2.1"],
    "has_evidence": true,
    "server": null
  },
  "draft_reply": {
    "lang": "ru",
    "text": "Здравствуйте! Ваше обращение принято. Информация будет проверена администратором в соответствии с пунктом 2.1 общих правил.",
    "cited": ["2.1"]
  },
  "needs_human": true,
  "confidence": 0.82,
  "reasons": [
    "Требуется проверка обстоятельств и приложенных материалов"
  ]
}

Это пример формата, а не обязательный текст ответа.

Не утверждать, что нарушение подтверждено, если система не располагает соответствующим решением администратора.

# 8. SAFETY & ESCALATION

Файл: `safety.py`

Это один из важнейших модулей проекта.

Обязательно создать централизованный список условий передачи обращения человеку.

## 8.1. Безусловная передача человеку

Всегда:

1. Платежи.
2. Возврат средств.
3. Апелляции банов.
4. Запросы на разблокировку аккаунтов.
5. Подозрения на взлом аккаунта.

Дополнительно передавать человеку:
- обращения с недостаточной уверенностью;
- неоднозначные жалобы;
- обращения без необходимых сведений;
- случаи, в которых не удалось найти подходящие правила;
- ошибки генерации или проверки цитирования.

## 8.2. Confidence

У каждого результата должен быть показатель confidence в диапазоне от 0 до 1.

Не считать confidence LLM достоверной вероятностью правильного ответа.

Разделять:
- confidence классификации;
- уверенность извлечения фактов;
- уверенность поиска;
- итоговое решение об эскалации.

Предусмотреть настраиваемые пороги.

Не устанавливать пороги произвольно без проверки на контрольной выборке.

## 8.3. Safety Gate

Перед возвратом результата:
- проверить обязательные условия эскалации;
- проверить корректность цитат;
- проверить отсутствие запрещённых обещаний;
- проверить соответствие языка;
- проверить структуру JSON.

При ошибке безопаснее передать обращение человеку.

# 10. MAKE PREDICT

Обязательная команда:

make predict IN=tickets.jsonl OUT=pred.jsonl

Требования:
- чтение JSONL;
- обработка всех записей;
- применение той же логики, что используется API;
- сохранение одного JSON-объекта на каждое входящее обращение;
- отсутствие дополнительных логов внутри pred.jsonl;
- корректная обработка больших файлов;
- сохранение исходного порядка записей;
- обработка ошибок отдельных записей без потери всего набора.

Дополнительно реализовать:
make train
make test
make evaluate
make run

Проверить работу команд на реальных данных.
